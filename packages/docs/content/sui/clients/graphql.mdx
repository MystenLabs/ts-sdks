`SuiGraphQLClient` talks to the Sui GraphQL API. It implements the same client API as
`SuiGrpcClient`, so anything on [Querying data](/sui/clients/querying) and
[Signing and execution](/sui/transactions/signing-and-execution) works here unchanged:

```typescript
import { SuiGraphQLClient } from '@mysten/sui/graphql';

const client = new SuiGraphQLClient({
	url: 'https://graphql.mainnet.sui.io/graphql',
	network: 'mainnet',
});

const { object } = await client.getObject({
	objectId: '0x...',
	include: { content: true },
});
```

On top of that shared surface, GraphQL gives you things a per-method RPC cannot: batching many reads
into a single round trip, point-in-time and historical reads, and custom selection sets that fetch
exactly the fields you need. The rest of this page covers those.

The constructor takes:

| Option    | Description                                                    |
| --------- | -------------------------------------------------------------- |
| `url`     | GraphQL endpoint                                               |
| `network` | Network the endpoint serves, used for caching and MVR defaults |
| `headers` | Extra headers sent with every request, such as an API key      |
| `fetch`   | Custom `fetch` implementation                                  |
| `queries` | Named documents callable through [`execute`](#named-queries)   |
| `mvr`     | Move Registry overrides                                        |

## Writing queries

Use `query` to run any GraphQL document against the endpoint:

```typescript
import { graphql } from '@mysten/sui/graphql/schema';

const chainIdentifierQuery = graphql(`
	query {
		chainIdentifier
	}
`);

const result = await client.query({ query: chainIdentifierQuery });

console.log(result.data?.chainIdentifier);
```

### Type safety

The `graphql` function is powered by [`gql.tada`](https://gql-tada.0no.co/), which types results and
variables from the schema itself — no code generation step and no hand-written result types. Fields
you did not select are not on the result type, and variables are checked against the query:

```typescript
const getSuinsName = graphql(`
	query getSuiName($address: SuiAddress!) {
		address(address: $address) {
			defaultNameRecord {
				domain
			}
		}
	}
`);

async function getDefaultSuinsName(address: string) {
	const result = await client.query({
		query: getSuinsName,
		variables: { address },
	});

	return result.data?.address?.defaultNameRecord?.domain;
}
```

### Using typed documents with other clients

The `graphql` function returns document nodes implementing the
[`TypedDocumentNode`](https://github.com/dotansimha/graphql-typed-document-node) standard, so the
same typed documents work with most GraphQL clients:

```tsx
import { useQuery } from '@apollo/client';
import { graphql } from '@mysten/sui/graphql/schema';

const chainIdentifierQuery = graphql(`
	query {
		chainIdentifier
	}
`);

function ChainIdentifier() {
	// Result types flow through the other client's own hooks and methods
	const { data } = useQuery(chainIdentifierQuery);

	return <span>{data?.chainIdentifier}</span>;
}
```

### Handling errors

`query` returns `{ data, errors }` rather than throwing on GraphQL errors, because a response can be
partially successful — some fields resolved, others failed. Check `errors` before trusting `data`:

```typescript
const { data, errors } = await client.query({ query: chainIdentifierQuery });

if (errors?.length) {
	throw new AggregateError(errors.map((error) => new Error(error.message)));
}
```

A transport-level failure — a non-2xx response — throws `SuiGraphQLRequestError` instead.

### Named queries

Pass a `queries` map when constructing the client and call them by name with `execute`. This keeps
query documents in one place instead of threading them through your call sites:

```typescript
const client = new SuiGraphQLClient({
	url: 'https://graphql.mainnet.sui.io/graphql',
	network: 'mainnet',
	queries: {
		getSuinsName,
		chainIdentifier: chainIdentifierQuery,
	},
});

const result = await client.execute('getSuinsName', {
	variables: { address: '0xabc...' },
});
```

Results and variables stay typed from the document the name resolves to.

## Native queries

Three things are worth writing a custom query for, because the shared API has no equivalent:

- **Batching.** One document can read many entities at once, and can combine unrelated reads that
  would otherwise be separate round trips.
- **Historical reads.** Objects, packages, and addresses can be read at a past version or
  checkpoint, rather than only as they are now.
- **Richer filters.** Transaction and event queries accept combinations and checkpoint bounds beyond
  the single predicate the shared [history queries](/sui/clients/querying#transactions-and-events)
  expose.

See the [GraphQL reference](https://docs.sui.io/references/sui-graphql) for the schema — which
fields exist and what arguments each one takes.

## Live data

The Sui GraphQL schema defines only `Query` and `Mutation` root types. There is no `subscription`
operation and no subscribe method on the client, so follow live activity by polling — or use
[gRPC subscriptions](/sui/clients/grpc#subscriptions) when you need server push.

### Cursor polling

Read the current tip once in descending order, then poll forward from `startCursor`. Because `after`
is an exclusive ledger-position bound, each poll returns only what has landed since the last one,
with no overlap and no gaps:

```typescript
const latest = await client.listEvents({
	filter: { emitModule: '0xpkg...::my_module' },
	order: 'descending',
	limit: 1,
});

let cursor = latest.startCursor;

while (true) {
	const page = await client.listEvents({
		filter: { emitModule: '0xpkg...::my_module' },
		after: cursor,
		limit: 50,
	});

	for (const event of page.events) {
		await handleEvent(event);
	}

	// Only advance the cursor once the page is fully handled
	cursor = page.endCursor ?? cursor;

	// Drain a backlog without waiting, otherwise pause before polling again
	if (!page.hasNextPage) {
		await new Promise((resolve) => setTimeout(resolve, 2000));
	}
}
```

Persist `cursor` if the consumer needs to survive restarts. The same pattern works with
`listTransactions`.

To follow whole checkpoints rather than one filtered feed, write a custom query using the
`afterCheckpoint` filter and track sequence numbers instead of cursors. Querying `checkpoint` with
no arguments returns the latest indexed checkpoint, which is the upper bound the poller works
toward.

<Callout type="warn">
	GraphQL reads an index that trails execution slightly, so a transaction `executeTransaction` has
	already returned may not appear in a query for a moment. Use `waitForTransaction` when you need to
	read your own write.
</Callout>
