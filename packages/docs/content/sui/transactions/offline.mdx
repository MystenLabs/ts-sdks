`Transaction.build()` can query a client to turn a transaction description into signable BCS bytes.
Depending on the transaction, it can resolve object IDs to versioned references, resolve transaction
intents, fetch the reference gas price, estimate the gas budget, select gas payment, and set replay
protection.

To build without a client, provide every required value before calling `build()`. This is useful for
backend services, air-gapped signing, and transaction pipelines that fetch state separately from
construction. See also the Sui documentation on
[offline signing](https://docs.sui.io/guides/developer/transactions/transaction-auth/offline-signing)
for the protocol-level details.

## Build the transaction kind only

Use `onlyTransactionKind` when the next system only needs the programmable transaction inputs and
commands. A transaction-kind build omits the sender, expiration, gas price, gas budget, gas owner,
and gas payment:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
	target: '0xPackageId::module::function_name',
	arguments: [tx.pure.u64(100)],
});

const kindBytes = await tx.build({ onlyTransactionKind: true });
```

`onlyTransactionKind` skips gas resolution, but it does not skip resolution of transaction inputs or
intents. Supply complete object references for object inputs, construct address-balance withdrawals
directly, or pass a client when those values still need to be looked up.

## Build full transaction bytes

A full offline build requires the sender and complete gas data:

| Method            | Description                                                               |
| ----------------- | ------------------------------------------------------------------------- |
| `setSender()`     | Address executing the transaction                                         |
| `setGasPrice()`   | Reference gas price obtained from the target network                      |
| `setGasBudget()`  | Maximum gas to spend, in MIST                                             |
| `setGasPayment()` | Versioned SUI coin references, or `[]` to pay from address balance        |
| `setGasOwner()`   | Gas owner for a sponsored transaction; defaults to the transaction sender |

These values determine the signed transaction, so gather them for the same network and recent state
that will execute the transaction. Gas budget estimation requires simulation and therefore a client;
an offline builder must set the budget explicitly.

### Pay gas from address balance

Set an empty gas payment to pay gas from the gas owner's SUI address balance. The gas owner defaults
to the sender. A transaction without a versioned, address-owned input also needs `ValidDuring`
expiration for replay protection:

```typescript
import { Transaction } from '@mysten/sui/transactions';

// Gather these values from the target network before going offline.
const sender = '0xSenderAddress';
const referenceGasPrice = 1_000n;
const currentEpoch = 100;
const chainIdentifier = 'Base58ChainIdentifier';

const tx = new Transaction();

// A FundsWithdrawal contains the amount and type, so it needs no object lookup.
const [coin] = tx.moveCall({
	target: '0x2::coin::redeem_funds',
	typeArguments: ['0x2::sui::SUI'],
	arguments: [tx.withdrawal({ amount: 1_000_000_000 })],
});
tx.transferObjects([coin], '0xRecipientAddress');

tx.setSender(sender);
tx.setGasPrice(referenceGasPrice);
tx.setGasBudget(50_000_000);
tx.setGasPayment([]);

tx.setExpiration({
	ValidDuring: {
		minEpoch: currentEpoch,
		maxEpoch: currentEpoch + 1,
		minTimestamp: null,
		maxTimestamp: null,
		chain: chainIdentifier,
		nonce: 0,
	},
});

const bytes = await tx.build();
```

The address balance must cover the gas budget in addition to any explicit SUI withdrawals. Do not
add the gas budget to a `tx.withdrawal()` amount; the protocol accounts for gas separately.

`Epoch` expiration alone does not replace the replay protection required for address-balance gas
when the transaction has no versioned, address-owned input. Use `ValidDuring` in that case.

### Pay gas with coin objects

To pay with coin objects, provide their exact versions and digests. This is also required when a
command refers to `tx.gas`:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.setSender('0xSenderAddress');
tx.setGasPrice(1_000);
tx.setGasBudget(50_000_000);
tx.setGasPayment([
	{
		objectId: '0xGasCoinId',
		version: '3',
		digest: 'Base58GasCoinDigest',
	},
]);

const [coin] = tx.splitCoins(tx.gas, [1_000_000]);
tx.transferObjects([coin], '0xRecipientAddress');

const bytes = await tx.build();
```

An explicit gas payment is preserved by `build()`.

## Resolve transaction inputs offline

### Shared and party objects

Shared and party object references use a stable `initialSharedVersion`, so they can be constructed
without looking up the current object version:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.moveCall({
	target: '0xPackageId::module::function_name',
	arguments: [
		tx.sharedObjectRef({
			objectId: '0xSharedObjectId',
			initialSharedVersion: '1',
			mutable: true,
		}),
	],
});
```

### Party objects

Party objects are address-owned but consensus-versioned, with per-address permissions. They are
referenced the same way as shared objects:

```typescript
tx.sharedObjectRef({
	objectId: '0xPartyObjectId',
	initialSharedVersion: '1',
	mutable: true,
});
```

Their offline-building properties are:

- **No version lookup needed**: `initialSharedVersion` is stable and set once when the object
  becomes a party object
- **Enable pipelining**: Submit multiple transactions on the same party object without waiting for
  each one to finalize
- **Cannot be used for gas**: Use address balance or a SUI coin object for gas payment

### Owned and immutable objects

When your transaction uses owned or immutable objects, you must provide the exact version and digest
for each one:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();

// Owned objects need exact version and digest
tx.transferObjects(
	[
		tx.objectRef({
			objectId: '0xOwnedObjectId',
			version: '42',
			digest: 'abc123...',
		}),
	],
	'0xRecipientAddress',
);

// Receiving objects also need exact version and digest
tx.moveCall({
	target: '0xPackage::module::receive',
	arguments: [
		tx.objectRef({
			objectId: '0xParentId',
			version: '10',
			digest: 'def456...',
		}),
		tx.receivingRef({
			objectId: '0xReceivingId',
			version: '5',
			digest: 'ghi789...',
		}),
	],
});
```

An actual address-owned, versioned input provides replay protection. With such an input, an offline
transaction can use address-balance gas without `ValidDuring`:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.transferObjects(
	[
		tx.objectRef({
			objectId: '0xOwnedObjectId',
			version: '42',
			digest: 'Base58ObjectDigest',
		}),
	],
	'0xRecipientAddress',
);

tx.setSender('0xSenderAddress');
tx.setGasPrice(1_000);
tx.setGasBudget(50_000_000);
tx.setGasPayment([]);

const bytes = await tx.build({ assumeSufficientAddressBalances: true });
```

The option allows the offline build to proceed because the SDK cannot determine from an object
reference whether it is address-owned or immutable. If the input is immutable, execution still
rejects address-balance gas without other replay protection. Shared and party object references do
not satisfy this requirement.

## Resolve coin and balance intents

`tx.coin()` and `tx.balance()` normally inspect the sender's address balance and coin objects during
intent resolution. For predictable offline construction, use `tx.withdrawal()` with
`coin::redeem_funds` or `balance::redeem_funds`, as shown above.

When the builder can assume that the sender has enough address balance, the
`assumeSufficientAddressBalances` option resolves these intents without balance or coin lookups:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const tx = new Transaction();
tx.transferObjects(
	[tx.coin({ type: '0xPackageId::module::TOKEN', balance: 1_000_000 })],
	'0xRecipientAddress',
);

const kindBytes = await tx.build({
	onlyTransactionKind: true,
	assumeSufficientAddressBalances: true,
});
```

<Callout type="warn">
	This option skips availability checks. The transaction can build successfully and then fail at
	execution if the required address balances are unavailable.
</Callout>

For SUI, the option does not force every intent to use address balance. Default SUI intents continue
to use `GasCoin` when another command already refers to `tx.gas`; otherwise they use address
balance. Setting `useGasCoin: false` always selects address balance. Do not combine those intents
with SUI intents that use the default behavior or set `useGasCoin: true`.

For a full build, the option can set gas payment to `[]` when payment is unset and the transaction
does not use `tx.gas`. Sender, gas price, gas budget, inputs, and replay protection must still be
provided as described above.

## JSON serialization and BCS building

`toJSON()` serializes the editable transaction representation. It prepares async thunks and
unsupported intents for serialization, but does not perform the full object and gas resolution done
by `build()`:

```typescript
import { Transaction } from '@mysten/sui/transactions';

const json = await tx.toJSON();
const restoredTx = Transaction.from(json);
```

If the transaction contains an intent whose resolver needs network data, either pass a client,
resolve it manually, or preserve it for a receiving system that supports it:

```typescript
const json = await tx.toJSON({
	supportedIntents: ['CoinWithBalance'],
});
```

Build BCS bytes only when the transaction is ready for signing or execution:

```typescript
const bytes = await restoredTx.build();
```

`Transaction.from()` accepts JSON, BCS byte arrays, and base64-encoded BCS strings.
